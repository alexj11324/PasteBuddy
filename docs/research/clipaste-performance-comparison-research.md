# Clipaste performance comparison research

**Audit date:** 2026-09-02  
**Pinned source:** `master` at [`941609c2080d0f1f13b9702c5a09a080fd47e3da`](https://github.com/gangz1o/Clipaste/tree/941609c2080d0f1f13b9702c5a09a080fd47e3da).  
**Scope:** GitHub README, source tree, and the visible `v2.2.11`–`v2.2.13` release notes only. No PasteBuddy source was inspected.

## Bottom line

Clipaste has a concrete large-history performance architecture: bounded payloads, actor-backed SwiftData, detached enrichment, lazy/paged UI loading, cancellation/generation gates, and bounded render/image caches. However, the README and releases make qualitative “fast/responsive” claims rather than reporting latency, CPU, memory, throughput, or test-dataset results. The source therefore supports architectural claims, not a claim that Clipaste is measurably faster.

## Findings

| Area | Observed Clipaste implementation | Later local comparison hook (no PasteBuddy claim) |
|---|---|---|
| Clipboard capture | A detached background sleeper polls `NSPasteboard.changeCount` (default 0.5 s), then hops to `@MainActor` to read and classify pasteboard items. Text, PNG/TIFF, image-file URLs, and selected rich representations are assembled into typed payloads before a detached utility persistence task is queued. [`ClipboardMonitor.swift`](https://github.com/gangz1o/Clipaste/blob/941609c2080d0f1f13b9702c5a09a080fd47e3da/clipaste/Managers/ClipboardMonitor.swift#L5-L24) [`ClipboardMonitor.swift`](https://github.com/gangz1o/Clipaste/blob/941609c2080d0f1f13b9702c5a09a080fd47e3da/clipaste/Managers/ClipboardMonitor.swift#L101-L121) [`ClipboardMonitor+Capture.swift`](https://github.com/gangz1o/Clipaste/blob/941609c2080d0f1f13b9702c5a09a080fd47e3da/clipaste/Managers/ClipboardMonitor%2BCapture.swift#L21-L129) | Check event/poll cadence, whether pasteboard bytes and classification run on the main actor, and whether rapid changes are coalesced or preserved. |
| Persistence and payloads | `ClipboardRecord` is a SwiftData model. Local/cloud stores live under Application Support; large text uses inline `plainText` plus `.externalStorage` `fullTextData`, while images, previews, icons, RTF, and the rich-text archive also use external storage. Text is split at 200,000 UTF-8 bytes (and may be user-truncated for iCloud); images are capped at 64 MB/100 million pixels. A content hash drives actor-side upsert/deduplication, followed by a save and change notification per payload. [`ClipboardModelContainerFactory.swift`](https://github.com/gangz1o/Clipaste/blob/941609c2080d0f1f13b9702c5a09a080fd47e3da/clipaste/Managers/ClipboardModelContainerFactory.swift#L21-L35) [`ClipboardRecord.swift`](https://github.com/gangz1o/Clipaste/blob/941609c2080d0f1f13b9702c5a09a080fd47e3da/clipaste/Models/ClipboardRecord.swift#L4-L38) [`ClipboardTextSyncPolicy.swift`](https://github.com/gangz1o/Clipaste/blob/941609c2080d0f1f13b9702c5a09a080fd47e3da/clipaste/Managers/ClipboardTextSyncPolicy.swift#L3-L47) [`ClipboardImageResourcePolicy.swift`](https://github.com/gangz1o/Clipaste/blob/941609c2080d0f1f13b9702c5a09a080fd47e3da/clipaste/Services/ClipboardImageResourcePolicy.swift#L3-L20) [`ClipboardStoreActor+RecordCommands.swift`](https://github.com/gangz1o/Clipaste/blob/941609c2080d0f1f13b9702c5a09a080fd47e3da/clipaste/Managers/ClipboardStoreActor%2BRecordCommands.swift#L5-L123) | Check the authoritative store, write serialization and save granularity, hash/dedup semantics, blob externalization, and whether capture reports persistence failure rather than only logging it. |
| Search/indexing | The database path uses SwiftData `FetchDescriptor` with `localizedStandardContains` over `plainText` and app name; no separate FTS/vector index or query-plan evidence appears in the audited tree. The UI filters loaded snapshots asynchronously after a 200 ms debounce, checks cancellation every 32 items, then issues one database supplement capped at 200 results when the in-memory history window is incomplete. [`ClipboardSearcher.swift`](https://github.com/gangz1o/Clipaste/blob/941609c2080d0f1f13b9702c5a09a080fd47e3da/clipaste/Managers/ClipboardSearcher.swift#L4-L40) [`ClipboardViewModel+Filtering.swift`](https://github.com/gangz1o/Clipaste/blob/941609c2080d0f1f13b9702c5a09a080fd47e3da/clipaste/ViewModels/ClipboardViewModel%2BFiltering.swift#L47-L150) | Check full-text index type, indexed fields (including OCR/long text), cancellation, and completeness beyond the first search page. Source caveat: the predicate searches stored `plainText`, while snapshots keep only the first 500 characters; the 200-row supplement can omit later matches. [`ClipboardStorageModels.swift`](https://github.com/gangz1o/Clipaste/blob/941609c2080d0f1f13b9702c5a09a080fd47e3da/clipaste/Managers/ClipboardStorageModels.swift#L31-L80) |
| Concurrency and side work | Writes and searches use `@ModelActor`; read waits are wrapped in detached user-initiated tasks. OCR, syntax highlighting, link metadata, and RTF rendering are detached/background work. Image downsampling uses a concurrent queue; link metadata is limited to four concurrent fetches and coalesced by hash. Capture creates one tracked detached task per change, while each task processes its payloads sequentially. [`StorageManager.swift`](https://github.com/gangz1o/Clipaste/blob/941609c2080d0f1f13b9702c5a09a080fd47e3da/clipaste/Managers/StorageManager.swift#L4-L43) [`StorageManager+RecordCommands.swift`](https://github.com/gangz1o/Clipaste/blob/941609c2080d0f1f13b9702c5a09a080fd47e3da/clipaste/Managers/StorageManager%2BRecordCommands.swift#L55-L203) [`LinkMetadataEngine.swift`](https://github.com/gangz1o/Clipaste/blob/941609c2080d0f1f13b9702c5a09a080fd47e3da/clipaste/Managers/LinkMetadataEngine.swift#L5-L31) | Check actor/queue boundaries, cancellation and stale-result rejection, burst behavior, duplicate-work suppression, and explicit concurrency limits for enrichment. |
| UI update strategy | The panel owns one `@State` view model. It hydrates a warm cache of 80 items, renders `LazyHStack`/`LazyVStack`, loads 80 first and 160-item pages near the tail, caps the resident history window at 2,000, and trims back to 80 when idle. Record-change notifications update one item; broader data notifications trigger a reload. RTF uses a 200-entry LRU and images use a 256-entry/64 MB `NSCache`; quick-paste geometry is installed only while its modifier is held. [`ClipboardPanelRootView.swift`](https://github.com/gangz1o/Clipaste/blob/941609c2080d0f1f13b9702c5a09a080fd47e3da/clipaste/Managers/ClipboardPanelRootView.swift#L5-L18) [`ClipboardHistoryWarmCache.swift`](https://github.com/gangz1o/Clipaste/blob/941609c2080d0f1f13b9702c5a09a080fd47e3da/clipaste/Services/ClipboardHistoryWarmCache.swift#L3-L20) [`ClipboardViewModel+HistoryLoading.swift`](https://github.com/gangz1o/Clipaste/blob/941609c2080d0f1f13b9702c5a09a080fd47e3da/clipaste/ViewModels/ClipboardViewModel%2BHistoryLoading.swift#L5-L91) [`ClipboardViewModel+RecordRefresh.swift`](https://github.com/gangz1o/Clipaste/blob/941609c2080d0f1f13b9702c5a09a080fd47e3da/clipaste/ViewModels/ClipboardViewModel%2BRecordRefresh.swift#L5-L45) [`ClipboardVerticalListView.swift`](https://github.com/gangz1o/Clipaste/blob/941609c2080d0f1f13b9702c5a09a080fd47e3da/clipaste/Views/ClipboardVerticalListView.swift#L108-L151) [`ListRenderEngine.swift`](https://github.com/gangz1o/Clipaste/blob/941609c2080d0f1f13b9702c5a09a080fd47e3da/clipaste/Views/ListRenderEngine.swift#L12-L69) [`ClipboardImagePipeline.swift`](https://github.com/gangz1o/Clipaste/blob/941609c2080d0f1f13b9702c5a09a080fd47e3da/clipaste/Managers/ClipboardImagePipeline.swift#L21-L45) | Check first-screen latency, page trigger/retention policy, incremental versus full invalidation, per-card payload loading, cache bounds, and stale-task guards. |

## Benchmark evidence and limits

- The README claims fast large-history browsing and responsive large-text handling, but reports no numbers or test protocol. [`README.md`](https://github.com/gangz1o/Clipaste/blob/941609c2080d0f1f13b9702c5a09a080fd47e3da/README.md#L81-L120)
- `v2.2.11`–`v2.2.13` release notes describe cancellation, paging, render-loop, cache/layout, and resource-limit improvements and mention regression coverage, but provide no p50/p95 latency, CPU, memory, throughput, item-count, or device/build measurements. [`v2.2.11`](https://github.com/gangz1o/Clipaste/releases/tag/v2.2.11) [`v2.2.12`](https://github.com/gangz1o/Clipaste/releases/tag/v2.2.12) [`v2.2.13`](https://github.com/gangz1o/Clipaste/releases/tag/v2.2.13)
- The source-level `StabilityHardeningSourceTests` checks that architectural patterns exist or are absent; it is not a runtime benchmark. [`StabilityHardeningSourceTests.swift`](https://github.com/gangz1o/Clipaste/blob/941609c2080d0f1f13b9702c5a09a080fd47e3da/scripts/StabilityHardeningSourceTests.swift#L3-L96)

For a later PasteBuddy comparison, limit conclusions to source/runtime-checkable mechanisms above and require a matched workload (history count, text/image sizes, burst rate) with panel-open, capture-to-persist, search, CPU, and memory measurements. This note makes no PasteBuddy performance assessment.
